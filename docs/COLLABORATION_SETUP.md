# 협업 검토함 설치·사용

## 현재 바로 가능한 것

GitHub Pages의 **협업 검토함 → 로컬 체험**에서 요청 목록·전후 값·승인/재수정·변경 영역 표시를 확인한다. 이 모드는 이 브라우저의 예제 데이터이며 외부 클라이언트 제출이나 실제 FTP 반영이 아니다.

서버 준비 전에도 클라이언트의 검토 요청 파일을 담당자에게 전달하고, 해당 홈페이지 편집기의 표시 JSON 입력에서 바로 읽어 변경 영역을 확인할 수 있다. 이 파일 검토는 서버의 공식 승인이나 FTP 반영 권한을 생성하지 않는다.

실제 서비스는 세 부분으로 구성된다:

1. GitHub Pages 또는 서버에서 제공하는 STYLE FORGE 웹 + Chrome 확장.
2. 별도 Node.js 22 이상 / HTTPS 협업 서버.
3. 담당자 Mac의 Node 기반 승인 적용 프로그램.

**카페24 쇼핑몰 HTML 스킨은 2번 서버를 설치하는 공간이 아니다.** 별도 Node 실행 서버와 주소가 필요하다. 현재 외부 서비스는 배포하지 않았다.

## 로컬에서 실제 계정·제출 테스트

Mac 터미널에서 저장소를 준비하고 다음을 실행한다.

```sh
npm ci --ignore-scripts
npm run server:init
npm run server
```

`server:init`에서 담당자 이메일/이름/비밀번호를 터미널로 입력한다. 비밀번호 입력은 화면에 표시되지 않는다. 기본 계정이나 공개 비밀번호는 없다. 데이터는 `~/.style-forge/server/database.json`에 저장되고 비밀번호는 scrypt로 해시 처리한다. 승인 서명용 개인키도 이 파일에 있으므로 공개·Git·웹 스킨에 업로드하지 않는다.

브라우저에서 `http://127.0.0.1:4319` → 협업 검토함 → 협업 서버 연결 → 주소 `http://127.0.0.1:4319` → 담당자 로그인.

담당자 설정에서 클라이언트 계정(초기 비밀번호 12자 이상)과 프로젝트를 만든다. 프로젝트의 사이트 주소는 실제 쇼핑몰 origin이다. 클라이언트 계정을 선택해 접근 범위를 지정한다. 초기 계정 전달은 별도 안전한 경로로 한다. 앱이 이메일을 자동 발송하지는 않는다.

로컬 loopback 주소는 본인 Mac에서만 접속된다. 외부 클라이언트가 이 주소로 접속할 수는 없다.

## 실제 온라인 서버 배포

Node.js 22 이상을 지원하는 별도 서버/VPS의 전용 계정에서 저장소를 받고 `npm ci --omit=dev --ignore-scripts`를 실행한다. 브라우저용 번들은 Git에 포함되어 있으므로 서버에서 재빌드할 필요 없다. `server:init`을 그 서버 터미널에서 실행한다.

환경 설정:

| 이름 | 의미 |
| --- | --- |
| `SF_DATA_DIR` | 전용 비공개 영속 데이터 폴더. 기본 `~/.style-forge/server` |
| `PORT` | 기본 4319 |
| `SF_BIND` | 기본 127.0.0.1. HTTPS reverse proxy 뒤에서 사용 |
| `SF_ALLOWED_ORIGINS` | 쉼표로 분리한 정확한 frontend origin. 와일드카드 사용하지 않음 |

기본 origin은 `https://millo0o.github.io`와 고정 확장 ID `chrome-extension://ecffoldmoeolonhekgaolmcllmngdokh`이다. 설정값을 지정하면 전체 목록을 대체하므로 둘 다 보존한다. 같은 서버 origin은 별도로 허용한다. 직접 변경한 manifest key나 웹 스토어 게시 ID를 사용하면 origin도 갱신해야 한다.

서버 프로세스는 단일 인스턴스로 실행하고 private 영속 폴더를 백업한다. JSON 원자적 저장을 사용하며 현재 50 MB까지의 작은 협업 공간을 위한 버전이다. 여러 worker/컨테이너에서 동일 파일을 공유하지 않는다. HTTPS reverse proxy는 `Host`를 보존하고 이 프로세스의 loopback 포트로 전달한다. 실제 도메인과 TLS 인증서를 구성해야 한다. 공개 HTTP로 비밀번호를 보내지 않는다. reverse proxy 측 요청 제한·프로세스 재시작·DB 백업은 서버 운영 설정에서 구성한다.

클라이언트에게는 협업 서버 HTTPS 주소와 계정만 전달한다. FTP 정보는 전달하지 않는다. 서버/API 자체에 FTP 비밀번호를 저장하지 않는다.

## 클라이언트 수정안 제출

1. 최신 확장 ZIP을 다시 설치/갱신한다. 고정 key를 추가했으므로 예전 unpacked 확장은 새 폴더를 다시 로드해야 할 수 있다.
2. 쇼핑몰에서 확장 실행 → 스타일 편집 → **검토 요청 보내기**.
3. 확장 자체의 검토함이 열리면 협업 서버 주소를 입력하고 해당 host의 접근 권한을 허용한다. 로그인 입력은 실제 쇼핑몰의 DOM에 들어가지 않는다.
4. 클라이언트 계정으로 로그인 → 프로젝트·제목·메모 → 제출.
5. 웹 체험/일반 웹 편집에서는 **검토 요청 파일**을 다운로드해 협업 검토함의 수정안 제출에 불러온다. 여러 페이지의 파일을 같이 선택할 수 있다.

요청에는 URL, selector, 수정 CSS, 대표 요소의 변경 전 값, 파일 위치 후보와 메모를 저장한다. 스킨 전체 소스나 FTP 비밀번호는 보내지 않는다. `product_no`, `cate_no` 등 query 값은 페이지를 구분한다. 인증 query가 있는 페이지는 일반 주소로 바꿔야 한다. 새로고침하면 로그인 토큰은 사라져 다시 로그인한다.

## 담당자 검토와 실제 페이지 표시

목록에서 페이지 주소/항목 수/전후 값을 확인한다. **홈페이지 표시 JSON**을 다운로드하여 실제 해당 페이지의 확장에서 **홈페이지 표시 JSON 불러오기**로 읽는다. 현재 URL의 요소를 찾아 표시하고 수정 CSS를 임시 미리보기로 적용한다. 원본 비교, 표시 끄기, 상위 요소 선택을 사용할 수 있다. 미확인 요소는 개수로 안내한다. 최대 100개 요소를 표시한다.

검토함에서 항목별 승인/반려/재수정 요청을 저장한다. 재수정 사유를 입력해야 클라이언트가 새 요청으로 답할 수 있다. 이전 요청과 검토 기록은 유지한다. 동시 검토는 version 충돌로 차단하며 새로고침을 요구한다.

## Mac 반영

협업 검토함의 **Mac 적용 프로그램**을 다운로드하고 `connector/README.md`를 따른다. Node.js 22 이상, 정확한 스킨 루트와 공통 레이아웃 경로가 필요하다. 담당자 설정에서 공개키를 받아 설정하고, 승인된 미적용 항목의 패키지를 다운로드한다.

프로그램은 원본을 읽어 `review.txt`의 전후 코드를 준비한다. 프로그램 안에서 사이트·원본 hash·공통 레이아웃 연결·CSS를 확인하고 APPLY를 입력해야 쓴다. FTP 직전에는 협업 서버 담당자로 로그인하여 승인 version/status를 다시 확인한다. 비밀번호는 저장하지 않는다. 승인 패키지는 24시간 유효하다.

성공 후 백업의 `receipt.json`을 검토함에 올리면 담당자의 적용 확인 기록을 남긴다. 이 기록은 담당자 신고이며 서버가 FTP 성공을 독립적으로 증명한 것은 아니다. 원격이 다시 바뀐 경우 자동 복원하지 않는다. SFTP, 비 UTF-8 레이아웃, </head>가 없는 레이아웃의 자동 연결은 현재 지원하지 않는다. 먼저 테스트 스킨에서 실제 카페24 loader 동작을 확인한다.
