# 실제 파일·FTP 반영을 위한 다음 단계

이 문서는 설계이며 현재 FTP 연결 프로그램이 구현되었다는 뜻이 아니다. v1.2의 편집 UI는 임시 CSS와 검토 가능한 코드를 완성한다.

## 권장 구조

```
실제 카페24 탭 + STYLE FORGE MV3
  ↔ Native Messaging 로컬 커넥터
  ↔ VS Code에서 사용하는 로컬 스킨 폴더
  ↔ 사용자가 설정한 SFTP / FTPS 연결
```

GitHub Pages의 정적 브라우저 앱에서는 FTP 소켓을 열지 않는다. Chrome Native Messaging으로 연결하는 로컬 프로그램을 기본 후보로 삼는다. 이 방식에는 운영체제별 설치 프로그램, 고정 extension ID와 명시적 추가 권한이 필요하다. localhost HTTP 방식은 브라우저의 Private Network Access/CORS 정책·인증을 별도로 해결해야 하므로 기본 구현으로 가정하지 않는다.

## 구현 순서

1. 로컬 폴더 루트·PC/모바일 스킨 지정, 파일 index와 SHA-256 기록.
2. FTP 계정의 호스트/프로토콜/대상 루트를 설정하고 읽기 작업으로 확인. 비밀번호는 UI의 보안 입력과 OS 자격 증명 저장소에서 취급하며 채팅·Git·로그에 남기지 않는다.
3. 원격 스킨을 별도 작업 폴더에 읽어 파일 인덱스를 갱신한다. 카페24 모듈은 실제 쇼핑몰 DOM과 연결하고 로컬에서 서버처럼 실행하려고 하지 않는다.
4. 편집 patch를 새 override CSS로 생성하고 기존 CSS/HTML 연결 위치에 대한 diff를 준비한다. 기존 selector를 일괄 치환하지 않는다.
5. 수정 후보 파일, 정확한 선택자·미디어·줄, 이전/이후 코드, 적용 사이트/스킨 루트를 사용자가 검토한다. 불명확한 매핑은 위치 확정을 먼저 요구한다.
6. 로컬 파일은 백업 및 원본 해시 재확인 후 임시 파일→원자적 교체로 저장한다. VS Code에서 동시에 수정되면 충돌을 표시한다.
7. 원격 업로드는 별도 명시적 적용 단계에서만 수행한다. 업로드 전 재다운로드·해시 비교와 recoverable 원격 원본 백업을 확보한다. 사용자 승인 없는 운영 업로드는 하지 않는다.
8. CSS 연결/배포 이후 실제 페이지에서 확인하며 문제 시 검토된 백업으로 복원한다.

## 다음 단계의 검증

먼저 합성 fixture와 임시 로컬 루트로 경로 탈출·중복 selector·인코딩·동시 수정·백업·rollback을 검증한다. 이후 테스트용 카페24 스킨과 연결 정보를 환경의 보안 저장 방식으로 제공받아 읽기를 검증한다. 운영 스킨에 바로 테스트 쓰기를 수행하지 않는다. 기존 FTP-simple 수동 업로드는 계속 사용할 수 있다.
